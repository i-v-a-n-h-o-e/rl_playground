# PPO для «Шофёра-убийцы»: проверка MPS

`PPO(device="mps")` работает на Apple Silicon: переносит на GPU вычисления
модели и обновление весов. В замере с одной средой CPU оказался в 10 раз
быстрее. Перенести текущую среду и весь цикл PPO одной сменой устройства
нельзя. Для отдельной реализации на GPU нужно решить, какие расхождения с
эталонным симулятором допустимы.

## Почему устройство модели не переносит среду

- [`ChauffeurPPOEnv.step`](../RL/chauffeur_ppo.py) передаёт состояние в
  `classical_feedback` и `step_feedback`. Те вычисляют управление пешехода,
  ищут первое пересечение оси, особых линий или круга захвата и при необходимости
  укорачивают шаг. Простой перенос формулы движения оставит эти расчёты на CPU.
- [Сборщик SB3](https://github.com/DLR-RM/stable-baselines3/blob/master/stable_baselines3/common/on_policy_algorithm.py)
  каждый шаг кладёт наблюдение на устройство модели и возвращает действие через
  `.cpu().numpy()`. [Буфер SB3](https://github.com/DLR-RM/stable-baselines3/blob/master/stable_baselines3/common/buffers.py)
  возвращает на CPU также значения и логарифмы вероятностей. NumPy хранит
  траектории и считает GAE, а при обновлении минибатчи снова отправляются на GPU.
- Симулятор различает близкие события в `float64`. [PyTorch MPS не поддерживает этот тип](https://docs.pytorch.org/docs/main/notes/mps.html#double-precision-types).
  При `dt=0.02`, `T=4` и нулевом рулении старт `(0, 2.3)` даёт захват ровно
  в дедлайн, а `(0, 2.3 + 1e-12)` — тайм-аут. Оба старта после округления
  дают одно и то же состояние `float32`. Замена типа уже на входе теряет
  различие, а здесь оно меняет суммарную награду с `0` на `−1`.

## Замеры

Нативный macOS 15.7.9 (Apple Silicon), PyTorch 2.13.0, SB3 2.9.2,
NumPy 1.26.4, один поток PyTorch, `PYTORCH_ENABLE_MPS_FALLBACK` выключен.

```bash
env -u PYTORCH_ENABLE_MPS_FALLBACK \
  uv run --project .python_env --locked python -m examples.benchmark_chauffeur_mps
```

В [`скрипте`](../examples/benchmark_chauffeur_mps.py) настройки из локального
прогона: seed 17, `MlpPolicy` с двумя слоями по 32, 1024 перехода на обновление,
минибатч 64, 10 эпох. Для каждой конфигурации три прогона по 8192 измеряемых
перехода после одного сбора и обновления для прогрева. Время MPS включает
ожидание устройства в конце каждой фазы. Вариант с четырьмя процессами
собирает по 256 шагов на среду: размер буфера тот же, длина отрезков GAE другая.

| Устройство PPO / сред | Сбор, с | Обновление, с | Всего, с | Переходов/с |
| --- | ---: | ---: | ---: | ---: |
| CPU / 1 | 1,88 | 1,38 | 3,26 | 2516 |
| MPS / 1 | 21,72 | 11,32 | 32,89 | 249 |
| CPU / 4 | 1,16 | 1,36 | 2,52 | 3249 |

Медианы фаз и суммы измерений посчитаны отдельно. На MPS медленнее и сбор,
и обновление: маленькие минибатчи и чтение метрик на CPU тоже создают накладные
расходы. Четыре процесса CPU дали на 29% больше переходов в секунду. Этот
замер сравнивает пропускную способность; качество политики не проверялось.

Metal-прототип считает только конец свободного движения за `dt=0.05` при
известных `phi` и `psi`. Вход и выход остаются на своём устройстве; засечены
1000 вызовов и синхронизация после них. Сравнение с векторным NumPy `float32`:

| Число состояний | NumPy, мкс на пакет | Metal, мкс на пакет |
| ---: | ---: | ---: |
| 1 | 16,9 | 10,1 |
| 64 | 18,9 | 7,0 |
| 1024 | 43,0 | 13,4 |
| 8192 | 219,7 | 18,7 |

Максимальное отклонение Metal от эталонной формулы CPU `float64` в этой
выборке — `6.5e-7` по координате. Время для одного состояния относится к
векторному NumPy и не сравнимо со скалярным шагом среды. Замер также не
включает обратную связь, события и запуск политики, поэтому по нему нельзя
предсказать ускорение обучения.

## Что имеет смысл переносить

Для текущей среды оставляем эталон на CPU. Если нужен отдельный эксперимент
на GPU, имеет смысл моделировать сразу много независимых эпизодов: батч
состояний, обратная связь пешехода, поиск событий, награды и сбросы в Metal
или тензорах MPS. Сбор траекторий и GAE потребуют тензорного цикла PPO вместо
сборщика SB3. Иначе синхронизация с CPU останется на каждом шаге.

Первый критерий для такого эксперимента — совпадение событий и исходов с CPU
на пограничных тестах и фиксированной сетке из 6532 стартов при одинаковых
действиях. Если допускаются различия, нужно заранее определить допуск и
измерить их отдельно. Затем стоит сравнивать время до одинакового качества
политики. Проверка только координат и шагов в секунду этого не показывает.
